# 安全说明

使用 Docker 本身并不等于安全。本文说明 witden 提供哪些保护、依赖哪些前提，以及部署方还需要做哪些工作。

## 1. 平台提供的保护

| 目标 | 措施 |
|---|---|
| AI 的操作只发生在所属的虚拟电脑内 | 所有 AI 工具都经过执行网关，只能访问这项工作固定的那台虚拟电脑；没有在服务器上直接执行的途径；虚拟电脑不可用时工作等待或失败，不会改用其他机器。 |
| AI 拿不到服务器或容器管理权限 | 只有 Docker Manager 持有 Docker 权限，API 只能请求它执行白名单内的操作，Worker 完全没有 Docker 权限。虚拟电脑容器不挂载 Docker socket，也不挂载宿主机上的任何路径，只挂载平台管理的数据卷：自己的持久化目录，以及所有虚拟电脑共用、以只读方式挂载的执行代理数据卷（其中只有平台安装的执行代理程序，文件全部属于 root，不含任何虚拟电脑的数据或密钥，虚拟电脑不能修改，也不能借它访问其他虚拟电脑）。容器移除全部 Linux capabilities 后只加回少量常用的能力，禁止提权（`no-new-privileges`），禁止特权模式和主机网络。 |
| 虚拟电脑内不使用 root | 模板和 Docker Manager 都拒绝以 root（名称、uid 或 gid 为 0）运行；执行代理自身也拒绝以 root 运行；镜像中没有 sudo。系统软件包由 Docker Manager 安装和卸载：它通过 `docker exec` 以 root 身份执行固定的 apt 命令，只接受软件包名称，并以清空的环境变量启动，虚拟电脑内的环境变量、执行代理令牌和用户目录中的程序都不会进入这个 root 进程。镜像自带的软件包不能卸载。Docker Manager 另外只在自己的容器中以 root 执行一条固定的安装命令，把平台镜像中的执行代理写入执行代理数据卷。 |
| 执行代理不可冒充 | 每台虚拟电脑的访问令牌在每次创建容器时重新签发，数据库只保存其哈希；连接时校验虚拟电脑和令牌，失败记录审计。这台虚拟电脑的执行代理在线并能应答时，再用同一令牌连接会被拒绝并记录审计（`runner.duplicate`），不会把连接交给后来者；只有原连接已经不再应答时，新的连接才会接替它。不允许访问网络的虚拟电脑经 Docker Manager 的管理通道连接，这个通道由 Docker Manager 在容器内打开，本身就证明了是哪台虚拟电脑，通过它启动的执行代理不带令牌。 |
| 令牌只有执行代理拿得到 | 虚拟电脑内的所有程序（包括 AI 员工执行的命令、桌面上的程序）都以同一个普通用户运行。witden 的镜像这样保护令牌：只有执行代理得到令牌，桌面服务等其他程序启动时就不带它；持有令牌的进程（容器的 1 号进程、启动进程和执行代理）都从只能执行、不能读取的程序文件启动，Linux 因此禁止同一用户的其他进程查看它们的环境变量和内存，也不能调试它们。执行代理不会从虚拟电脑用户可写的目录加载代码：启动进程只使用镜像自带的执行代理，或执行代理数据卷中全部文件属于 root、其他用户不可写的版本，两者都从同一个只能执行的程序启动，得到的环境变量相同。虚拟电脑页的“Runner 令牌”一栏显示这台虚拟电脑是否受保护。 |
| 断线后不重复操作 | 有副作用的操作结果不确定时，先查询执行代理的操作记录；无法确认时如实告诉模型，不自动重做。 |
| 复制环境不带凭据 | 复制虚拟电脑时剔除模板声明的凭据路径（如 `~/.ssh`、浏览器配置、`~/.aws`）；连同凭据复制需要“管理模型与密钥”权限。 |
| 密钥不外泄 | 模型密钥、通讯凭据和虚拟电脑的模型访问密钥使用主密钥加密（AES-256-GCM）保存，Tunnel token 只保存在专用数据卷中；它们只能由人在控制台中填写或更换，接口和界面从不返回或显示，只显示是否已设置。例外是 Webhook 来源的密钥：它由系统生成，以哈希校验发送方，同时用主密钥加密保存一份，控制台账号可以在来源卡片上显示和复制，每次读取记入审计；系统管理员和其他 AI 员工仍然读不到。日志、审计和工具输出中的密钥会被遮盖。 |
| 虚拟电脑内的模型访问不泄露真实密钥 | 虚拟电脑内只有内部地址和平台为这台虚拟电脑签发的密钥；请求经执行代理的已认证连接回到平台，平台核对密钥和允许的模型后，用真实密钥转发。签发的密钥由执行代理写入虚拟电脑，控制台不显示，离开这台虚拟电脑无效，可以随时更换或关闭；只有自己有权使用某个模型的成员才能把它开放给虚拟电脑。 |
| 权限不依赖提示词 | 工具是否可用、能和哪些 AI 员工协作、可以读取哪些资料、哪些操作需要审批，都由服务器检查；提示词（包括 AI 员工的“人设与工作方式”）只用于说明工作方式。 |
| 工具授权可限定本次运行 | 审批卡片的“本次运行内允许”仅免除当前任务本次运行中同名工具后续调用的重复审批，包括不同参数；不增加工具权限、不修改 AI 员工设置，也不传给子任务或其他 AI 员工。下一轮对话、任务重试或完成后续做重新审批；因紧急停止或接管暂停、之后继续的同一次运行保留授权，禁用 AI 员工和紧急停止仍生效。普通“批准”只批准当前调用。 |
| 只有有效的 @ 才会触发工作 | 在控制台中必须从 @ 列表中选择 AI 员工；AI 员工之间只能通过专门的工具相互 @，回答正文中提到的名称不会触发其他 AI 员工。同一话题内的 @ 只能 @ 已在话题中的 AI 员工，不会把其他 AI 员工拉进话题。AI 员工之间协作的范围由话题决定：AI 员工只能 @、委托和转交给同一话题中的 AI 员工，不需要权限；无论在群组话题还是私信中，工作都不会交给话题外的 AI 员工，委托和转交（包括人在控制台中转交）也不会让 AI 员工加入任何话题，当前话题的内容不会进入话题外 AI 员工的上下文（AI 员工在 AI 员工对话中主动发出的消息除外，见下文）。AI 员工之间自动往来的轮次有上限；对话拆出或委托的工作结果回到对话后又引出新工作，以及 AI 员工之间转交任务，也计入同一上限，直到有人发言。 |
| 失败即关闭 | 没有处理的 AI 员工的外部会话不接收请求：通讯接入没有选择默认处理的 AI 员工时，跟随默认的会话都是如此。 |
| 外部会话只有一位 AI 员工 | Slack、飞书、GitHub 的会话中只有处理这个会话的 AI 员工工作，默认是接入选择的那一位，控制台账号可以为单个会话另选一位已启用的 AI 员工（不能是系统管理员）。它不能请其他 AI 员工进来，控制台不能邀请其他 AI 员工加入；会话换成另一位 AI 员工后（另选，或跟随默认的会话随接入更换），原 AI 员工离开会话，它在那里的工作随即停止，更换记入审计。对外始终以机器人的身份发言。控制台中的话题不能发布到外部频道。 |
| 实时事件与入站正文 | 实时事件在数据提交后才发出；通讯平台同步事件处理完成后清除临时正文。话题 webhook 的原始正文和查询参数作为专用历史保留至手动清理，不写入审计或实时事件；认证、Cookie、签名等请求头被遮盖。 |
| 自动触发有明确授权 | 触发器由控制台管理员配置；开启“自动化管理”权限的 AI 员工只能管理自己负责、位于它参与的话题中的触发器，读不到也设不了密钥，并且只在控制台账号请求的工作中可用；新建的 AI 员工这项权限默认为“询问”，默认每次调用由管理员批准，也可由管理员明确授权在本次运行内使用同一工具。每个触发器指定话题和处理的 AI 员工。收到 webhook 后先认证、持久保存、过滤，再按配置人的授权交给 AI 员工；配置人停用或离开话题、AI 员工失去参与资格时不再发起工作。系统管理员不能处理触发器。 |
| 过滤代码不能操作主机 | 前置过滤在独立的 QuickJS WebAssembly 解释器中执行，不提供网络、文件、进程和平台接口；限制执行时间为 100 毫秒、内存为 16 MiB，只接受同步布尔返回值，错误或超限时不调用模型。 |
| Webhook 历史按话题读取 | 管理员可查看历史；外部成员需能查看对应话题；AI 员工的 `read_webhook_history` 只读当前话题，移除 AI 员工后失去访问资格。原始正文不会自动广播到关联的外部频道；AI 员工有权读到的资料仍可能出现在其回答中。 |
| 发出的文件受控 | AI 员工只能用“分享文件”把自己虚拟电脑中的文件作为附件发到话题。系统接口（`/proc`、`/sys`、`/dev` 下的路径）和含有已知格式密钥（如 `sk-`、`xoxb-`、`ghp_`、执行代理令牌 `wdr_`）的文件一律拒绝，并记录审计。发往 Slack 的附件只能是这个话题自己的文件。 |
| 消息中的地址不会被自动请求 | AI 员工在消息正文中写的图片地址不会被自动加载：控制台把外部图片显示为链接，点击才打开；发往 Slack 时关闭链接和媒体预览；发往 GitHub 时图片改为链接。这样不会有人替 AI 员工访问它写下的地址，地址中夹带的内容也就不会被带给第三方。 |
| 卡片中的小应用在沙箱中运行 | AI 员工写的小应用（HTML、CSS、JavaScript）只在控制台中、在隔离的沙箱框架里运行：没有同源权限，读不到控制台的登录状态和数据，不能调用控制台接口；内容安全策略禁止一切网络访问（不能请求接口、加载外部脚本、样式、字体或图片），不能提交表单、打开弹窗或对话框、跳转整个页面。控制台页面不允许任何框架加载页面（`frame-src 'none'`），所以小应用也不能把自己的框架跳转到别的网站或 data: 页面来带出数据，这样的尝试会让它重新载入，反复尝试则停止运行。内容安全策略管不到 WebRTC：控制台去掉了小应用中的 WebRTC 接口，并移除它在自己里面创建的框架（新框架会重新带有这个接口），移除不了就停止运行；这是控制台尽力而为的限制，不是浏览器保证的边界，所以不要在小应用中输入密码、密钥等敏感内容。它只能通过受控的接口保存自己在这个浏览器中的状态，或请求提交卡片上的操作——提交前控制台会显示随附的数据，由人确认。飞书、Slack、GitHub 中不运行小应用，只显示文字说明。 |
| 关联只连接外部会话与内部话题，只开放直接发送和工作状态 | 话题之间的关联由控制台账号建立，只能建立在外部会话（Slack、飞书、GitHub）和内部话题（控制台中的话题和私信）之间，关联私信需要再次确认。关联只允许 AI 员工用 `send_message` 主动发送，不开放对方话题的记录，也不把任务直接交给对方话题中的 AI 员工；原始请求人、来源和自动轮次由服务器记录，模型不能指定。外部成员、外部会话和自动事件带来的限制随消息一起传递，并延续到由它引出的 @、委托、任务结果和定时跟进：这些工作不能修改职责说明、自动化规则和技能，也不能写入 AI 员工记忆；每一跳计入自动轮次上限。发往外部会话的消息只发布，不在本地运行 AI 员工。解除关联后不能再发送，对方未读的关联消息作废，由关联开始的任务结束。外部会话的 AI 员工还可以用 `linked_topic_status` 查看关联的内部话题的工作状态：进行中和最近完成的任务的标题、进度、结果摘录，以及本会话发去的请求的处理情况，不包含消息、执行记录和文件。这些内容可能由 AI 员工转述给外部会话中的人，与内部话题发回的消息一样不经额外审批；摘录在截取前遮盖密钥，系统管理员的配置工作不列出，关联的是私信时只显示本会话发去的请求的处理情况。不希望外部会话中的人了解某个话题的工作时，不要关联这两个话题。 |
| AI 员工之间的对话逐个授权，只交换消息 | AI 员工只能主动给管理员在它的“可以主动对话的 AI 员工”（`allowed_contacts`）中逐个选择的 AI 员工发消息，授权只在这个方向上生效，在发送时由服务器检查，不需要审批；对方回复不需要授权，对方主动发新消息需要它自己的授权。系统管理员既不能主动联系其他 AI 员工，也不能被选为对象；在 Slack、飞书、GitHub 的会话中工作时不提供这个工具。消息和回复只出现在两位 AI 员工之间的“AI 员工对话”中（没有成员，管理员只能查看，不能发言、邀请、关联或添加触发器，其中的任务不能转交）：接收方读不到发送方所在的话题、记录和文件，发送方只收到回复；来源话题和任务由服务器记录，不给接收方看。接收方按自己的权限工作，外部成员、外部会话和自动事件带来的限制随消息传递；每一次发送和回复都计入自动轮次上限。发送方自己决定发出什么内容：它在消息中写入的当前话题资料会被对方看到，提示中要求只写对方需要的内容。 |
| AI 员工只读取所在的话题 | AI 员工只能查阅和搜索它所在话题的消息，没有读取其他话题的工具，任何权限设置都不改变这一点。其他话题的内容只能这样到达 AI 员工：它作为参与者在那个话题中工作；经管理员建立的关联，外部会话与内部话题之间互发的消息，以及外部会话的 AI 员工查看的关联内部话题的工作状态（不含消息正文）；或在话题之外与被允许的 AI 员工直接对话时对方发来的回答。私信和 AI 员工对话始终只属于其中的人和 AI 员工。 |
| 权限决定 AI 员工能用什么 | AI 员工能读取哪些资料由它的权限决定：知识空间、按接入和类别授权的飞书与 GitHub 工具。有权读取的内容，AI 员工可以在它工作的任何地方使用，包括发到 Slack、飞书会话和公开的 GitHub 仓库；witden 不追踪资料来源，也不按来源暂扣。需要限制时，收窄 AI 员工的权限，或把相应工具设为“询问”；AI 员工服务外部成员或公开仓库时，只给它在那里可以公开的资料。 |
| AI 员工记忆只由管理员的工作写入 | AI 员工记忆在 AI 员工工作的所有地方随系统提示词给出：只有管理员请求的工作（在控制台中，或来自已关联到管理员账号的 Slack、飞书、GitHub 账号）才能让 AI 员工写入，外部成员的请求一律拒绝；“记忆”权限默认需要审批。系统管理员不能修改自己的 AI 员工记忆。 |
| AI 员工的技能只由管理员的工作修改 | 技能决定 AI 员工在所有地方怎样做某类工作：每个技能的名称和说明随系统提示词给出，内容由 AI 员工按需读取。AI 员工只能修改自己的技能，并且只在管理员请求的工作中（在控制台中，或来自已关联到管理员账号的 Slack、飞书、GitHub 账号）可以新建、修改和删除；外部成员的请求，以及外部会话的输入、Webhook 和定时触发引出的工作一律拒绝，与 AI 员工记忆相同。“技能”权限默认始终允许，可以改为“询问”或禁用；每次新建、修改和删除都记入审计，不记录说明和内容。系统管理员没有技能。技能的文件（脚本、模板等）保存在平台上，同样只能由管理员在控制台中、或由 AI 员工在上述管理员请求的工作中修改；AI 员工从虚拟电脑的目录保存技能时，被拒绝的请求不会读取任何文件，含有已知格式密钥的文件一律拒绝。 |
| 写入虚拟电脑的技能只来自 AI 员工自己 | AI 员工读取技能时，平台只把它自己已保存的这个技能（`SKILL.md` 和技能的文件）写入它自己虚拟电脑中的 `~/.witden/skills/<名称>/`，先删除这个目录再写入；与其他文件操作一样经执行网关，需要这项工作有“文件”权限，没有时只把内容和文件列表交给 AI 员工。技能的脚本不由平台运行，由 AI 员工用自己的命令行权限在虚拟电脑中运行，边界就是虚拟电脑本身的边界。技能会写入这位 AI 员工的虚拟电脑，复制 AI 员工时也写入副本所在的虚拟电脑，同一台虚拟电脑上的 AI 员工都能读到，因此不要在技能中放入只应留在某台虚拟电脑中的内容。 |
| 删除消息即从上下文中去掉 | 消息被删除时（在 Slack、GitHub 中删除了原消息，或清理话题数据；控制台中不能编辑或删除单条消息），回应它的那一轮从 AI 员工的对话上下文中移除（这一轮还在进行时先停止），尚未读到它的对话不会再读到；话题中其他记录里原样出现的内容被替换。对话摘要中对它的转述无法逐字识别，需要彻底去掉时清空该对话的上下文。 |
| 外部成员受限 | 通讯接入为未关联的人自动创建的外部成员只能使用该接入选择的 AI 员工，以及这个接入的会话中另选的、处理这个会话的 AI 员工（只在那个会话中），不能登录控制台；会话换成另一位 AI 员工后，他们与原 AI 员工在那里正在进行的工作立即取消。 |
| 系统管理员不越权 | 系统管理员是内置的 AI 员工，只有一个（数据库约束保证），不能停用、复制或另外添加，它的设置只能由人修改。它通过与控制台相同的接口修改配置，以提问的管理员身份执行，审计记录写明 AI 员工和任务；只开放配置相关的接口（不包括账号与身份关联、消息、文件、任务、审批、在虚拟电脑中执行命令和接管），请求中带有密钥字段一律拒绝，不能修改任何系统管理员。它只接受控制台中管理员的请求：不能作为外部会话处理的 AI 员工（包括接入默认处理的 AI 员工），不在与外部会话关联的话题中工作，也不接受其他 AI 员工的联系和委托，自己也不能主动联系其他 AI 员工。在单独的 Worker 进程中，配置调用经内部令牌交给 API 进程执行。 |
| 控制台账号就是管理员 | 能登录控制台的账号都是管理员，可以查看全部会话，包括 Slack、飞书中的私信。只把控制台账号发给负责管理 witden 的人。 |
| 紧急停止不可绕过 | 停止期间的审批只记录决定，解除后才执行；按任务停止时覆盖其全部委托工作。 |
| 转交不带走权限和执行过程 | 人和对话只能转交没有执行、也没有待处理的审批、委托、提问或定时跟进的任务。执行任务的 AI 员工转交自己的任务时，转交在这一轮结束、Worker 释放领取之前才生效，生效前重新检查全部条件；在此之前任务被取消或被紧急停止的，转交作废。人和 AI 员工都只能转交给已在话题中、已启用的 AI 员工，转交不会邀请 AI 员工加入话题，需要时由人先邀请；任务有未决的审批或未结束的委托时不能转交。接手的 AI 员工以原请求人的身份重新经过授权检查，按自己的权限配置工作（委托出来的任务仍不超过委托方），原 AI 员工已获得的审批不再有效。之前的执行步骤保留在任务记录中，不进入接手方的上下文。私信只有一位 AI 员工，私信中的任务不能转交。 |
| 接管不会长期阻塞 AI 工作 | 管理员接管虚拟电脑需要浏览器持续确认；离开、长时间不操作或浏览器异常关闭时自动交还。 |

## 2. 部署方需要做的工作

1. **保护 Docker Manager。** 它相当于服务器的管理权限：只放在内部网络中（Compose 中的 `control` 网络），设置足够长的 `WITDEN_MANAGER_TOKEN`，并通过 `DOCKER_GID` 只把 Docker socket 的访问权限授予它。条件允许时，使用 rootless Docker，或让 Docker Manager 通过 `DOCKER_HOST` 管理一台专用主机或虚拟机。
2. **限制虚拟电脑连接端口。** 虚拟电脑通过宿主机网关访问 8330 端口。使用 `WITDEN_HUB_BIND` 把它绑定到 Docker 网桥地址（如 `172.17.0.1`），不要暴露到公网。该端口本身要求每台虚拟电脑的令牌。
3. **需要更强隔离时使用安全运行时。** 处理敏感数据的模板可以设置 `runtime: runsc`（gVisor）或 Kata Containers，并在 `WITDEN_ALLOWED_RUNTIMES` 和 `WITDEN_MANAGER_ALLOWED_RUNTIMES` 中启用。
4. **规划网络。** 虚拟电脑默认连接 `witden-computers` 网桥（虚拟电脑之间不能互相访问），可以访问外网和宿主机网关。宿主机上的数据库等服务应只监听 `127.0.0.1` 或使用防火墙隔离。不需要外网的模板使用 `network: internal` 或 `none`。
5. **保管主密钥和令牌。** 设置 `WITDEN_SECRET_KEY` 并离线备份，丢失后已保存的密钥无法解密；`WITDEN_INTERNAL_TOKEN` 只提供给 API 和 Worker。
6. **保护控制台。** 只在内部网络中开放，并在前面放置 HTTPS 反向代理。不要把控制台端口（8320）转发到公网：外部平台只需要访问事件端口（8325），它只提供各平台的事件接口、不需要登录的地址检查接口、Slack 安装回调（只完成控制台中发起的安装，校验签名的 state）和 AI 员工头像，其他请求一律返回 404。控制台保存公网事件地址前会确认它只通往事件端口，见[部署与配置](deployment.md#24-公网事件地址)。使用 Cloudflare Tunnel 时，token 以文件形式保存在数据卷 `witden-tunnel` 中，只挂载给 `api`（读写）和 `tunnel`（只读）服务；持有 token 的人可以接管这个 tunnel，请像主密钥一样保管。控制台账号都是管理员，可以看到所有会话（包括 Slack、飞书中与机器人的私信），请据此告知使用机器人的人。
7. **配置 Slack。** 优先使用 Socket Mode：它不需要公网地址，App-Level Token 只授予 `connections:write`；使用事件地址时必须设置 Signing Secret；只把机器人邀请到需要的频道。
8. **配置飞书。** 优先使用长连接：它不需要公网地址，只用 App ID 和 App Secret 主动连到飞书；同一个飞书应用只接到一个 witden，否则消息会被另一个部署分走。使用事件地址时必须设置 Verification Token，并保持 Encrypt Key 为空。 飞书工具只给需要的 AI 员工、需要的公司和需要的功能，写入可以设为需要批准；以应用身份访问时，应用只能接触在飞书中授权给它的文档、表格和日历，请只把需要的内容授权给应用。从飞书读到的内容只在这家公司的飞书会话和控制台中自由流动，发往别处需要批准。
9. **配置 GitHub。** 作为机器人时必须设置 Webhook Secret；优先使用 GitHub App，只安装到需要的仓库，私钥只保存在 witden 中；使用机器人账号时，用专用账号，令牌只授予需要接入的仓库。只作为认证的账号（例如某个人自己的账号）不接收消息、不需要 Webhook，但 AI 员工能以这个人的身份操作：令牌只给需要的仓库和权限，并设置有效期；GitHub 工具只给需要的 AI 员工、需要的接入和需要的类别，写入（尤其是合并 pull request、提交文件、触发工作流）建议设为需要批准。经飞书、GitHub 工具写入前，witden 会检查写入的内容会被谁看到，带有他们看不到的资料时由资料的所有者批准。
10. **确定镜像来源。** Compose 默认从 GitHub Container Registry 拉取本项目 GitHub Actions 构建的镜像（`ghcr.io/zhaozhaozz/witden`），标签 `latest` 跟随 main 分支。生产环境建议用 `WITDEN_IMAGE_TAG` 固定到发布的版本或某个提交（`sha-<提交号>`），确认后再升级；需要自行审核镜像内容时，从源码构建镜像并设置 `WITDEN_IMAGE_REPO=witden`，见[部署与配置](deployment.md#22-docker-compose)。

## 3. 已知限制

- Webhook 来源使用持有密钥认证（请求头中的密钥，或 Standard Webhooks 签名；签名带时间戳，超过 5 分钟的请求被拒绝，同一 `webhook-id` 只处理一次），发送方必须通过 HTTPS 访问公网事件地址。密钥由系统生成，控制台账号可以随时复制，请只交给发送方。持有密钥的人可以触发所有使用这个来源的触发器，由各触发器指定的 AI 员工发起工作；JavaScript 过滤是业务条件，不替代鉴权。正文与查询参数不作内容脱敏，发送方不要放入无关凭据，管理员需按业务需要清理历史并在反向代理设置请求频率和存储容量限制。

- 同一台虚拟电脑上的 AI 员工共享文件、已安装的软件和登录状态；需要互相保密的工作必须分配到不同的虚拟电脑。虚拟电脑详情页会显示共享范围。
- 执行代理令牌的保护依赖 witden 镜像自带的启动方式（镜像标签 `witden.init=protected`，以及它的入口程序）。使用其他镜像，或基于 witden 镜像构建时改掉了入口（`ENTRYPOINT`）的镜像，虚拟电脑内的程序仍可能读到令牌，虚拟电脑页会显示“未保护”。令牌只能用来以这台虚拟电脑的身份连接执行网关的 8330 端口，因此请按[部署与配置](deployment.md)把该端口只绑定到 Docker 网桥地址（`WITDEN_HUB_BIND`）。
- 升级前创建的虚拟电脑仍运行旧镜像的容器，令牌不受保护，在虚拟电脑页点击“重置”并保留持久化目录中的数据后生效（见[部署与配置](deployment.md#6-升级)）。
- Compose 部署中，平台升级时安装的执行代理会在所有使用执行代理数据卷的虚拟电脑上生效。新版本在虚拟电脑中启动后反复立即退出时，这台虚拟电脑改用镜像自带的执行代理；需要退回旧版本时，用旧版平台镜像重新启动 Docker Manager 即可。
- 平台安装的软件包来自镜像中配置的 apt 软件源，安装脚本以 root 身份运行。虚拟电脑内的用户不能修改软件源；有“系统软件”权限的 AI 员工可以安装软件源中的任何软件包，需要时把这项权限设为“询问”或“禁用”。
- 管理员或 AI 员工在虚拟电脑中安装运行的其他程序（包括其他 AI 工具），拥有这台虚拟电脑上普通用户的全部能力，平台不逐条审批它们的操作；它们的边界就是虚拟电脑本身的边界（非 root、无 Docker socket、网络策略）。
- AI 员工启动的后台命令和终端会话会一直运行，直到 AI 员工停止它们，或虚拟电脑停止、重启、重置；任务或对话结束、紧急停止和接管都不会结束它们（紧急停止只暂停 AI 员工的工作）。需要立即结束时，管理员可以在虚拟电脑页的“控制台”中结束进程，或停止虚拟电脑；“会话”标签列出仍在运行的后台命令。命令的完整输出保存在虚拟电脑的 `~/.witden/commands/` 中，与虚拟电脑里的其他文件一样，同一台虚拟电脑上的 AI 员工都能读取。
- 桌面浏览器以 `--no-sandbox` 方式运行（容器内没有用户命名空间），依赖容器本身的隔离。
- 磁盘配额依赖存储驱动（overlay2 + xfs pquota）；不支持时，虚拟电脑状态中会提示“未强制”。
- 记忆检索目前基于关键词匹配。
- 飞书为实验性接入，只支持文本；企业微信尚未支持。
