# 安全说明

使用 Docker 本身并不等于安全。本文说明 witden 提供哪些保护、依赖哪些前提，以及部署方还需要做哪些工作。

## 1. 平台提供的保护

| 目标 | 措施 |
|---|---|
| AI 的操作只发生在所属的虚拟电脑内 | 所有 AI 工具都经过执行网关，只能访问这项工作固定的那台虚拟电脑；没有在服务器上直接执行的途径；虚拟电脑不可用时工作等待或失败，不会改用其他机器。 |
| AI 拿不到服务器或容器管理权限 | 只有 Docker Manager 持有 Docker 权限，API 只能请求它执行白名单内的操作，Worker 完全没有 Docker 权限。虚拟电脑容器不挂载 Docker socket，只挂载平台管理的数据卷，移除全部 Linux capabilities 后只加回少量常用的能力，禁止特权模式和主机网络；模板关闭“系统软件安装”时还禁止提权。 |
| 虚拟电脑内以普通用户运行 | 模板和 Docker Manager 都拒绝以 root（名称、uid 或 gid 为 0）运行；执行代理自身也拒绝以 root 运行。模板允许“系统软件安装”时（默认），虚拟电脑内的普通用户可以不输密码执行 `sudo apt-get`；apt 能以 root 身份运行任意命令，因此这相当于在虚拟电脑内拥有 root 权限。这个 root 仍受容器限制：只有上述能力，没有 Docker socket、宿主机目录和特权模式。关闭这项设置后，容器以 `no-new-privileges` 启动，虚拟电脑内无法提权。 |
| 执行代理不可冒充 | 每台虚拟电脑的访问令牌在每次创建容器时重新签发，数据库只保存其哈希；连接时校验虚拟电脑和令牌，失败记录审计。这台虚拟电脑的执行代理在线并能应答时，再用同一令牌连接会被拒绝并记录审计（`runner.duplicate`），不会把连接交给后来者；只有原连接已经不再应答时，新的连接才会接替它。不允许访问网络的虚拟电脑经 Docker Manager 的管理通道连接，这个通道由 Docker Manager 在容器内打开，本身就证明了是哪台虚拟电脑，通过它启动的执行代理不带令牌。 |
| 令牌只有执行代理拿得到 | 虚拟电脑内的所有程序（包括角色执行的命令、桌面上的程序）都以同一个普通用户运行。witden 的镜像这样保护令牌：只有执行代理得到令牌，桌面服务等其他程序启动时就不带它；持有令牌的进程（容器的 1 号进程、启动进程和执行代理）都从只能执行、不能读取的程序文件启动，Linux 因此禁止同一用户的其他进程查看它们的环境变量和内存，也不能调试它们。执行代理不会从虚拟电脑用户可写的目录加载代码。虚拟电脑页的“Runner 令牌”一栏显示这台虚拟电脑是否受保护。 |
| 断线后不重复操作 | 有副作用的操作结果不确定时，先查询执行代理的操作记录；无法确认时如实告诉模型，不自动重做。 |
| 复制环境不带凭据 | 复制虚拟电脑时剔除模板声明的凭据路径（如 `~/.ssh`、浏览器配置、`~/.aws`）；连同凭据复制需要“管理模型与密钥”权限。 |
| 密钥不外泄 | 模型密钥、通讯凭据和虚拟电脑的模型访问密钥使用主密钥加密（AES-256-GCM）保存，Tunnel token 只保存在专用数据卷中；它们只能由人在控制台中填写或更换，接口和界面从不返回或显示，只显示是否已设置。日志、审计和工具输出中的密钥会被遮盖。 |
| 虚拟电脑内的模型访问不泄露真实密钥 | 虚拟电脑内只有内部地址和平台为这台虚拟电脑签发的密钥；请求经执行代理的已认证连接回到平台，平台核对密钥和允许的模型后，用真实密钥转发。签发的密钥由执行代理写入虚拟电脑，控制台不显示，离开这台虚拟电脑无效，可以随时更换或关闭；只有自己有权使用某个模型的成员才能把它开放给虚拟电脑。 |
| 权限不依赖提示词 | 工具是否可用、可以联系哪些角色、可以读取哪些资料、哪些操作需要审批，都由服务器检查；提示词只用于说明工作方式。 |
| 只有有效的 @ 才会触发工作 | 在控制台中必须从 @ 列表中选择角色；角色之间只能通过专门的工具相互 @，回答正文中提到的名称不会触发其他角色。角色之间自动往来的轮次有上限；对话拆出或委托的工作结果回到对话后又引出新工作，也计入同一上限，直到有人发言。 |
| 失败即关闭 | 成员列表未知或超过 30 分钟未刷新的私有外部会话（把话题发布到这里时，按整个工作区计算能看到它的人）、没有选择角色的通讯接入，一律按最严格的方式处理。 |
| 实时事件与入站正文 | 实时事件在数据提交后才发出；入站事件处理完成后即清除正文。 |
| 发出的文件受控 | 角色只能用“分享文件”把自己虚拟电脑中的文件作为附件发到话题。系统接口（`/proc`、`/sys`、`/dev` 下的路径）和含有已知格式密钥（如 `sk-`、`xoxb-`、`ghp_`、执行代理令牌 `wdr_`）的文件一律拒绝，并记录审计。发往 Slack 的附件只能是这个话题自己的文件。 |
| 消息中的地址不会被自动请求 | 角色在消息正文中写的图片地址不会被自动加载：控制台把外部图片显示为链接，点击才打开；发往 Slack 时关闭链接和媒体预览；发往 GitHub 时图片改为链接。这样不会有人替角色访问它写下的地址，地址中夹带的内容也就不会被带给第三方。 |
| 读取其他话题需要授权 | 角色读取其他话题是一项单独的权限，新角色默认禁用，可以设为“询问”；开启后可读取任何渠道的话题，读到的内容可在角色工作的任何地方使用。私信不能从其他话题读取。 |
| 权限决定角色能用什么 | 角色能读取哪些资料由它的权限决定：知识空间、按接入和类别授权的飞书与 GitHub 工具、读取其他话题。有权读取的内容，角色可以在它工作的任何地方使用，包括发到 Slack、飞书会话和公开的 GitHub 仓库；witden 不追踪资料来源，也不按来源暂扣。需要限制时，收窄角色的权限，或把相应工具设为“询问”；角色服务外部成员或公开仓库时，只给它在那里可以公开的资料。 |
| 角色记忆只由管理员的工作写入 | 角色记忆在角色工作的所有地方随提示词给出：只有控制台账号请求的工作才能让角色写入，外部成员的请求一律拒绝；“记忆”权限默认需要审批。系统管理员角色不能修改自己的角色记忆。 |
| 删除消息即从上下文中去掉 | 消息被删除时，回应它的那一轮从角色对话的上下文中移除（这一轮还在进行时先停止），尚未读到它的对话不会再读到；话题中其他记录里原样出现的内容被替换。对话摘要中对它的转述无法逐字识别，需要彻底去掉时清空该对话的上下文。 |
| 外部成员受限 | 通讯接入为未关联的人自动创建的外部成员只能使用该接入的机器人代表的角色，不能登录控制台；接入改为代表另一个角色后，他们与原角色正在进行的工作立即取消。 |
| 系统管理员角色不越权 | 系统管理员是内置角色，只有一个（数据库约束保证），不能停用、复制或另外添加，它的设置只能由人修改。它通过与控制台相同的接口修改配置，以提问的管理员身份执行，审计记录写明角色和任务；只开放配置相关的接口（不包括账号与身份关联、消息、文件、任务、审批、在虚拟电脑中执行命令和接管），请求中带有密钥字段一律拒绝，不能修改任何系统管理员角色。它只接受控制台中管理员的请求：不能作为外部机器人代表的角色，不在与外部会话关联的话题中工作，也不接受其他角色的联系和委托。在单独的 Worker 进程中，配置调用经内部令牌交给 API 进程执行。 |
| 控制台账号就是管理员 | 能登录控制台的账号都是管理员，可以查看全部会话，包括 Slack、飞书中的私信。只把控制台账号发给负责管理 witden 的人。 |
| 紧急停止不可绕过 | 停止期间的审批只记录决定，解除后才执行；按任务停止时覆盖其全部委托工作。 |
| 接管不会长期阻塞 AI 工作 | 管理员接管虚拟电脑需要浏览器持续确认；离开、长时间不操作或浏览器异常关闭时自动交还。 |

## 2. 部署方需要做的工作

1. **保护 Docker Manager。** 它相当于服务器的管理权限：只放在内部网络中（Compose 中的 `control` 网络），设置足够长的 `WITDEN_MANAGER_TOKEN`，并通过 `DOCKER_GID` 只把 Docker socket 的访问权限授予它。条件允许时，使用 rootless Docker，或让 Docker Manager 通过 `DOCKER_HOST` 管理一台专用主机或虚拟机。
2. **限制虚拟电脑连接端口。** 虚拟电脑通过宿主机网关访问 8330 端口。使用 `WITDEN_HUB_BIND` 把它绑定到 Docker 网桥地址（如 `172.17.0.1`），不要暴露到公网。该端口本身要求每台虚拟电脑的令牌。
3. **需要更强隔离时使用安全运行时。** 处理敏感数据的模板可以设置 `runtime: runsc`（gVisor）或 Kata Containers，并在 `WITDEN_ALLOWED_RUNTIMES` 和 `WITDEN_MANAGER_ALLOWED_RUNTIMES` 中启用。
4. **规划网络。** 虚拟电脑默认连接 `witden-computers` 网桥（虚拟电脑之间不能互相访问），可以访问外网和宿主机网关。宿主机上的数据库等服务应只监听 `127.0.0.1` 或使用防火墙隔离。不需要外网的模板使用 `network: internal` 或 `none`。
5. **保管主密钥和令牌。** 设置 `WITDEN_SECRET_KEY` 并离线备份，丢失后已保存的密钥无法解密；`WITDEN_INTERNAL_TOKEN` 只提供给 API 和 Worker。
6. **保护控制台。** 只在内部网络中开放，并在前面放置 HTTPS 反向代理。不要把控制台端口（8320）转发到公网：外部平台只需要访问事件端口（8325），它只提供各平台的事件接口、不需要登录的地址检查接口、Slack 安装回调（只完成控制台中发起的安装，校验签名的 state）和角色头像，其他请求一律返回 404。控制台保存公网事件地址前会确认它只通往事件端口，见[部署与配置](deployment.md#24-公网事件地址)。使用 Cloudflare Tunnel 时，token 以文件形式保存在数据卷 `witden-tunnel` 中，只挂载给 `api`（读写）和 `tunnel`（只读）服务；持有 token 的人可以接管这个 tunnel，请像主密钥一样保管。控制台账号都是管理员，可以看到所有会话（包括 Slack、飞书中与机器人的私信），请据此告知使用机器人的人。
7. **配置 Slack。** 优先使用 Socket Mode：它不需要公网地址，App-Level Token 只授予 `connections:write`；使用事件地址时必须设置 Signing Secret；按需授予 `chat:write.customize` 以显示角色名称和头像；只把机器人邀请到需要的频道。
8. **配置飞书。** 优先使用长连接：它不需要公网地址，只用 App ID 和 App Secret 主动连到飞书；同一个飞书应用只接到一个 witden，否则消息会被另一个部署分走。使用事件地址时必须设置 Verification Token，并保持 Encrypt Key 为空。 飞书工具只给需要的角色、需要的公司和需要的功能，写入可以设为需要批准；以应用身份访问时，应用只能接触在飞书中授权给它的文档、表格和日历，请只把需要的内容授权给应用。从飞书读到的内容只在这家公司的飞书会话和控制台中自由流动，发往别处需要批准。
9. **配置 GitHub。** 作为机器人时必须设置 Webhook Secret；优先使用 GitHub App，只安装到需要的仓库，私钥只保存在 witden 中；使用机器人账号时，用专用账号，令牌只授予需要接入的仓库。只作为认证的账号（例如某个人自己的账号）不接收消息、不需要 Webhook，但角色能以这个人的身份操作：令牌只给需要的仓库和权限，并设置有效期；GitHub 工具只给需要的角色、需要的接入和需要的类别，写入（尤其是合并 pull request、提交文件、触发工作流）建议设为需要批准。经飞书、GitHub 工具写入前，witden 会检查写入的内容会被谁看到，带有他们看不到的资料时由资料的所有者批准。

## 3. 已知限制

- 同一台虚拟电脑上的角色共享文件、已安装的软件和登录状态；需要互相保密的工作必须分配到不同的虚拟电脑。虚拟电脑详情页会显示共享范围。
- 执行代理令牌的保护依赖 witden 镜像自带的启动方式（镜像标签 `witden.init=protected`，以及它的入口程序）。使用其他镜像，或基于 witden 镜像构建时改掉了入口（`ENTRYPOINT`）的镜像，虚拟电脑内的程序仍可能读到令牌，虚拟电脑页会显示“未保护”。令牌只能用来以这台虚拟电脑的身份连接执行网关的 8330 端口，因此请按[部署与配置](deployment.md)把该端口只绑定到 Docker 网桥地址（`WITDEN_HUB_BIND`）。
- 升级前创建的虚拟电脑仍运行旧镜像的容器，令牌不受保护，在虚拟电脑页点击“重置”并保留持久化目录中的数据后生效（见[部署与配置](deployment.md#6-升级)）。
- 允许“系统软件安装”的虚拟电脑中，能执行 `sudo apt-get` 的程序可以以 root 身份改动执行代理的程序文件，从而在执行代理下次启动时拿到令牌，上面的令牌保护对它们不成立。需要令牌保护、或虚拟电脑内不允许 root 的工作，请使用关闭了这项设置的模板。
- 管理员或角色在虚拟电脑中安装运行的其他程序（包括其他 AI 工具），拥有这台虚拟电脑上普通用户的全部能力（允许“系统软件安装”时还包括 root 权限），平台不逐条审批它们的操作；它们的边界就是虚拟电脑本身的边界（容器的能力限制、无 Docker socket、网络策略）。
- 桌面浏览器以 `--no-sandbox` 方式运行（容器内没有用户命名空间），依赖容器本身的隔离。
- 磁盘配额依赖存储驱动（overlay2 + xfs pquota）；不支持时，虚拟电脑状态中会提示“未强制”。
- 记忆检索目前基于关键词匹配。
- 飞书为实验性接入，只支持文本；企业微信尚未支持。
