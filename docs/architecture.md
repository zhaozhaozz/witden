# 系统架构

本文介绍 witden 的组成部分、一项工作的处理过程，以及执行边界和可靠性方面的设计，供部署和评估 witden 的管理员参考。权限与资料保护的详细说明见[安全说明](security.md)。

## 1. 设计原则

- **外部编排，内部执行。** 平台负责身份、话题、权限、任务和模型调用；所有“动手”的操作（执行命令、读写文件、操作桌面和浏览器）只发生在角色所在的虚拟电脑内。
- **最小权限。** 只有 Docker Manager 能够管理容器；处理 AI 任务的 Worker 不持有任何 Docker 权限；虚拟电脑内一律以普通用户运行。
- **控制台即管理员，保护面向外部。** 能登录控制台的账号都是管理员，可以看到全部会话；需要保护的是 Slack、飞书、GitHub 上的人：未关联的人默认不能使用角色，内容发往那里之前检查信息流向。
- **默认拒绝、失败即关闭。** 信息不足以判断是否安全时，按最严格的方式处理。
- **可恢复。** 任务、入站和出站消息都持久保存在数据库中，进程重启后继续处理；操作结果不确定时不盲目重做。

## 2. 组件

| 组件 | 职责 | Docker 权限 |
|---|---|---|
| API 服务 | 网页控制台、REST API、实时事件流、虚拟电脑连接入口、执行网关、Slack 和飞书的事件接收（主动建立的长连接，或事件地址） | 无，通过 HTTP 请求 Docker Manager |
| Worker | 领取任务、运行角色（模型与工具的循环）、调用模型、向外部平台发送消息 | 无，通过 API 的执行网关操作虚拟电脑 |
| Docker Manager | 按白名单创建、启停、删除、备份、恢复虚拟电脑，统计资源 | 有，且只有它有 |
| 执行代理（Runner） | 运行在每台虚拟电脑内，执行命令、终端、文件、屏幕、键鼠和浏览器操作，记录每个请求的结果 | 无 |
| PostgreSQL | 业务数据、任务队列、入站和出站队列、事件通知 | — |
| Laya（可选） | 开源的 System 1 决策模型，供话题调度使用；只在内部网络中可访问 | 无 |

单进程部署时，API、Worker 和 Docker Manager 运行在同一个进程中，数据库使用内置的嵌入式 PostgreSQL。

## 3. 一项工作的处理过程

1. **接收消息。** 控制台的消息直接写入话题；Slack 等外部事件先验证签名，持久保存后立即确认，再按顺序处理，重复的事件会被去除。
2. **确定由哪些角色处理。** 来自 Slack、飞书、GitHub 的请求交给通讯接入的机器人代表的角色（一个机器人代表一个角色，没有选择角色的接入不接收请求）。控制台中依次考虑：消息中有效 @ 的角色；私信中的角色；话题设为“自动”时，话题中唯一的角色，或由调度模型（System 1 模型，见[使用指南](user-guide.md#8-话题调度)）选出的角色。角色之间的 @ 和委托交给对方角色。
3. **检查是否允许。** 管理员可以使用所有角色；外部成员只能使用其通讯接入的机器人代表的角色；角色请其他角色协作时，按发起角色“可以联系和委托的角色”检查；系统管理员角色只接受控制台中管理员的请求，不需要虚拟电脑；还会检查话题状态、角色的模型和虚拟电脑是否可用。不满足时在话题中说明原因。
4. **交给角色的对话。** 每个角色在每个话题、每个私信里有一段对话，它的上下文从一条消息延续到下一条。消息进入这段对话的待读列表：角色没有在工作时，开始新的一轮；正在工作时，消息并入进行中的这一轮，不会另起一份并行的工作。每一轮固定在角色当时所在的虚拟电脑上，记录角色配置的快照、本轮可用的工具范围，以及资料来源标记（用于输出前的检查）。
5. **执行。** Worker 领取工作，在模型与工具之间循环：每次调用模型之前，先把话题里的新消息、任务结果和到期的跟进加到对话末尾；模型决定下一步，工具调用经执行网关进入虚拟电脑，结果交回模型。模型给出回答时如果又有新内容到达，这一轮继续；否则结束。等待审批或虚拟电脑时暂停，期间到达的消息在恢复后读到。每一步都持久保存。
6. **独立任务。** 较大、可以单独完成的工作，角色可以拆成一项任务；委托给其他角色的工作也是任务。任务有自己的上下文，可以等待人工回答和它委托的工作，结束后结果回到发起它的对话。
7. **整理上下文。** 对话达到模型的整理点（默认是上下文长度的 3/4，可以按模型设置）时，模型把此前的内容写成摘要，摘要成为对话新的开头；原来的步骤仍保存在执行记录中。提示词和工具说明在每次请求时重新生成，不参与整理。为了让模型服务复用提示缓存，对话的开头在每次请求中保持不变，时间和提问人随新消息给出。
8. **输出。** 角色要发布的内容先检查资料能否让目的地的人看到（关联了 Slack、飞书会话时包括那里的成员），必要时暂扣并交给资料来源的管理员审批；通过后发布到话题，并同步到关联的外部会话。对话记住它读过的资料，因此一段对话读过受限资料后，之后的输出同样要经过检查。

## 4. 执行边界

- **执行网关**是 AI 访问虚拟电脑的唯一通道。每次操作都检查：所属工具在任务的工具范围内、任务仍在运行、虚拟电脑是任务固定的那一台且正在运行、没有成员接管、没有紧急停止、桌面操作持有桌面控制权。检查通过后记录操作，再发往虚拟电脑。
- **虚拟电脑的连接**：执行代理在虚拟电脑启动后主动连接平台，并用这台虚拟电脑专属的令牌认证（每次重建容器都会重新签发）；同一台虚拟电脑的执行代理在线时，平台不接受第二个连接。令牌只交给执行代理，虚拟电脑内的其他程序读不到（见[安全说明](security.md)）。不允许访问网络的虚拟电脑通过 Docker Manager 的管理通道连接，这个通道本身证明身份，不需要令牌。实时画面等虚拟电脑内的服务也经由同一连接转发，不对外开放端口。
- **不可用时等待**：虚拟电脑不可用时任务进入等待，超时后失败；恢复后重新执行同一个操作。平台不会改用其他虚拟电脑，也没有在服务器上直接执行的途径。

## 5. 虚拟电脑内部

- **命令与终端**：一次性执行命令；长时间运行或交互式的程序使用终端会话，可以输入、读取输出、发送按键、结束整组进程。
- **桌面**：图形桌面支持截图和键鼠操作；实时画面分为只读和可操作两路，只有正在接管的管理员能连接可操作的一路。
- **浏览器**：“桌面”模式使用桌面上可见的浏览器，管理员可以观看和接管；“后台”模式使用不显示的浏览器，不占用桌面。
- **模型访问（可选）**：开启后，执行代理在虚拟电脑内提供 OpenAI 兼容、Anthropic 和 System One 接口，把请求转回平台；平台核对签发的密钥和允许的模型后，用真实的服务地址和密钥调用模型，并按虚拟电脑统计用量。
- **其他程序**：管理员或角色可以在虚拟电脑中安装和运行任何程序。平台只管理自己的角色，不单独管理这些程序；它们的能力以虚拟电脑本身的边界为限。

## 6. 共享与接管

- 同一台虚拟电脑上的多个角色可以同时执行命令；鼠标、键盘和可见浏览器同一时间只由一个持有者使用（桌面控制权），任务等待、暂停或结束时自动释放。
- 管理员接管虚拟电脑时，这台虚拟电脑上的 AI 工作暂停，直到交还。接管需要浏览器持续确认：离开页面、浏览器标签在后台超过 30 秒或 5 分钟没有操作时，控制台自动交还；浏览器异常关闭时，接管在约 3 分钟后失效，平台自动恢复被暂停的工作。

## 7. 可靠性

- **持久队列**：对话的每一轮、任务、入站事件和出站消息都保存在 PostgreSQL 中，由多个进程安全地并发领取；进程崩溃后，未完成的工作由其他进程接手。对话的待读列表与“这一轮是否还在进行”在同一把行锁下判断，消息不会落在一轮结束和下一轮开始之间而无人处理。
- **操作结果不确定时**：有副作用的操作在连接中断后不会自动重做。平台先向执行代理查询该操作的记录：已完成就使用真实结果；无法确认就如实告诉模型“结果不确定”，由它先检查当前状态再决定。
- **不重复执行**：入站事件按消息去重；出站消息按“消息 × 目标频道”只发送一次，失败可见且可以重试；执行代理按请求编号去重。
- **事务与通知**：数据库事务保持简短，模型调用和虚拟电脑操作都在事务之外进行；实时事件在事务提交后才发出，因此控制台不会看到随后被撤销的数据。

## 8. 实时更新

控制台通过事件流实时接收新消息、任务状态、角色的工作进展和虚拟电脑状态。每个事件在推送前都会重新检查接收者能否查看；接收者都是管理员，可以看到全部会话。

配置发生变化时（角色、账号、模型、虚拟电脑、通讯接入、知识空间、平台设置），无论是在另一个浏览器中由人修改，还是由系统管理员角色修改，平台都会通知所有打开的控制台“哪一类配置变了”，相应的列表和侧边栏自动重新读取，不需要刷新页面。通知中只有类别，不含配置内容。

## 9. 数据存储

| 数据 | 位置 |
|---|---|
| 账号、外部成员、角色、话题、消息、角色的对话与上下文、任务、审批、审计、用量 | PostgreSQL |
| 模型密钥、通讯凭据 | PostgreSQL，使用主密钥加密 |
| 话题文件、头像 | 平台数据目录 |
| 虚拟电脑的文件 | 每台虚拟电脑的 Docker 数据卷 |
| 虚拟电脑备份 | Docker Manager 的数据目录 |
