# 系统架构

本文介绍 witden 的组成部分、一项工作的处理过程，以及执行边界和可靠性方面的设计，供部署和评估 witden 的管理员参考。权限与资料保护的详细说明见[安全说明](security.md)。

## 1. 设计原则

- **外部编排，内部执行。** 平台负责身份、话题、权限、任务和模型调用；所有“动手”的操作（执行命令、读写文件、操作桌面和浏览器）只发生在 AI 员工所在的虚拟电脑内。
- **最小权限。** 只有 Docker Manager 能够管理容器；处理 AI 任务的 Worker 不持有任何 Docker 权限；虚拟电脑内一律以普通用户运行，系统软件包由 Docker Manager 以固定的 apt 命令安装和卸载。
- **控制台即管理员，保护面向外部。** 能登录控制台的账号都是管理员，可以看到全部会话；需要保护的是 Slack、飞书、GitHub 上的人：未关联的人默认不能使用 AI 员工；AI 员工能读取什么由它的权限决定，有权读取的内容可以在它工作的任何地方使用。
- **默认拒绝、失败即关闭。** 信息不足以判断是否安全时，按最严格的方式处理。
- **可恢复。** 任务、入站和出站消息都持久保存在数据库中，进程重启后继续处理；操作结果不确定时不盲目重做。

## 2. 组件

| 组件 | 职责 | Docker 权限 |
|---|---|---|
| API 服务 | 网页控制台、REST API、实时事件流、虚拟电脑连接入口、执行网关、Slack 和飞书的事件接收（主动建立的长连接，或事件地址） | 无，通过 HTTP 请求 Docker Manager |
| Worker | 领取任务、运行 AI 员工（模型与工具的循环）、调用模型、向外部平台发送消息 | 无，通过 API 的执行网关操作虚拟电脑 |
| Docker Manager | 按白名单创建、启停、删除、备份、恢复虚拟电脑，统计资源 | 有，且只有它有 |
| 执行代理（Runner） | 运行在每台虚拟电脑内，执行命令、终端、文件、屏幕、键鼠和浏览器操作，记录每个请求的结果 | 无 |
| PostgreSQL | 业务数据、任务队列、入站和出站队列、事件通知 | — |
| Laya（可选） | 开源的 System 1 决策模型，供话题调度使用；只在内部网络中可访问 | 无 |

单进程部署时，API、Worker 和 Docker Manager 运行在同一个进程中，数据库使用内置的嵌入式 PostgreSQL。

## 3. 一项工作的处理过程

1. **接收消息。** 控制台的消息直接写入话题；Slack 等外部事件先验证签名，持久保存后立即确认，再按顺序处理，重复的事件会被去除。
2. **确定由哪些 AI 员工处理。** 来自 Slack、飞书、GitHub 的请求交给通讯接入的机器人代表的 AI 员工（一个机器人代表一位 AI 员工，没有选择 AI 员工的接入不接收请求）。控制台中依次考虑：消息中有效 @ 的 AI 员工；私信中的 AI 员工；话题设为“自动”时，话题中唯一的 AI 员工，或由调度模型（System 1 模型或普通对话模型，见[使用指南](user-guide.md#8-话题调度)）参考话题目标和各 AI 员工的职责说明选出的 AI 员工。AI 员工之间的 @、委托和转交交给同一话题中的对方 AI 员工；AI 员工在话题之外直接发给另一位 AI 员工的消息（`contact_role`）交给对方在两者“AI 员工对话”中的对话。
3. **检查是否允许。** 管理员可以使用所有 AI 员工；外部成员只能使用其通讯接入的机器人代表的 AI 员工；Slack、飞书、GitHub 的会话中只有这位 AI 员工工作，不能请其他 AI 员工进来；AI 员工之间协作的范围由话题决定：AI 员工只能 @、委托和转交给同一话题中的 AI 员工，不需要权限，工作不会交给话题外的 AI 员工，人转交任务时也一样；话题关联只连接外部会话与内部话题，外部会话的 AI 员工通过关联把工作交给内部话题；AI 员工只能主动联系管理员为它逐个允许的 AI 员工（单向），回复不需要授权；系统管理员只接受控制台中管理员的请求，不需要虚拟电脑；还会检查话题状态、AI 员工的模型和虚拟电脑是否可用。不满足时在话题中说明原因。
4. **交给 AI 员工的对话。** 每位 AI 员工在每个话题、每个私信里有一段对话，它的上下文从一条消息延续到下一条。消息进入这段对话的待读列表：AI 员工没有在工作时，开始新的一轮；正在工作时，消息并入进行中的这一轮，不会另起一份并行的工作。每一轮固定在 AI 员工当时所在的虚拟电脑上，记录 AI 员工配置的快照和本轮可用的工具范围。
5. **执行。** Worker 领取工作，在模型与工具之间循环：每次调用模型之前，先把话题里的新消息、任务结果和到期的跟进加到对话末尾；模型决定下一步，工具调用经执行网关进入虚拟电脑，结果交回模型。工具结果只在交回模型时按工具输出上限截取一次：超过上限时模型读到开头和结尾，完整内容写入 AI 员工虚拟电脑中的文件，由它按需分页读取或搜索。模型给出回答时如果又有新内容到达，这一轮继续；否则结束。一轮没有步数上限，只受 token 上限、取消和紧急停止约束。等待审批或虚拟电脑时暂停，期间到达的消息在恢复后读到。每一步都持久保存。
6. **独立任务。** 较大、可以单独完成的工作，AI 员工可以拆成一项任务；委托给其他 AI 员工的工作也是任务。任务有自己的上下文，可以等待人工回答和它委托的工作，结束后结果回到发起它的对话。已完成的任务可以补充要求：同一个任务以新的版本接着做，每次交付分别记录并送回对话。没有在执行、也没有等待中的事项的任务可以由人转交给同一话题中的其他 AI 员工：仍是同一个任务，接手的 AI 员工按自己的权限在自己的虚拟电脑上工作，上下文从交接简报开始；转交不会把 AI 员工邀请进话题。AI 员工停用后，它的任务等待同一话题中的其他 AI 员工认领。AI 员工也可以把任务转交给同一话题中的其他 AI 员工：执行中的任务由执行它的 AI 员工转交，工具调用只记下请求，这一轮随即结束，Worker 在运行结束、释放领取之前重新检查后才换手；在此之前到达的补充要求留给接手的 AI 员工，取消和紧急停止优先，转交随之作废。对话可以转交它拆出或委托出去、当前没有执行的任务。每次 AI 员工转交计入自动轮次上限。
7. **整理上下文。** 对话达到模型的整理点（默认是上下文长度的 3/4，可以按模型设置）时，模型把此前的内容写成摘要，摘要成为对话新的开头；原来的步骤仍保存在执行记录中。提示词和工具说明在每次请求时重新生成，不参与整理。系统提示词以 AI 员工的技能列表（只有名称、说明和文件个数，需要时用 `read_skill` 读取全文）和 AI 员工记忆结尾，二者在它工作的所有地方相同，只在有增删改时变化。技能可以带脚本和其他文件：`read_skill` 经执行网关把整个技能写入 AI 员工自己的虚拟电脑（`~/.witden/skills/<名称>/`，需要“文件”权限），AI 员工在那里运行脚本；`save_skill` 也可以从虚拟电脑中的一个目录保存整个技能。为了让模型服务复用提示缓存，对话的开头在每次请求中保持不变，时间和提问人随新消息给出。
8. **输出。** AI 员工要发布的内容直接发布到话题，并同步到关联的外部会话。AI 员工还可以用 `send_message` 发到与本话题直接关联的话题：外部会话发往内部话题的消息进入那里接收 AI 员工的对话（带着服务器记录的原始请求人、来源和自动轮次），内部话题发往外部会话的只经出站队列发布。由外部请求引出的 @、委托、任务结果和跟进都保留外部输入带来的限制。两位 AI 员工之间的直接对话发生在只有这两位 AI 员工的“AI 员工对话”中：服务器记录消息来自哪段对话或哪项任务，接收方这一轮的回答发在那里，并送回发送方原来的对话（或作为补充输入送回仍在进行的独立任务），接收方看不到发送方所在的话题。AI 员工只读取它所在话题的消息，没有读取其他话题的工具；其他话题的内容只经上述关联消息、关联话题的工作状态和直接对话中的回答到达它。AI 员工能用到哪些资料，取决于它的权限：有权读取的内容，可以在它工作的任何地方使用。

## 4. 执行边界

- **执行网关**是 AI 访问虚拟电脑的唯一通道。每次操作都检查：所属工具在任务的工具范围内、任务仍在运行、虚拟电脑是任务固定的那一台且正在运行、没有成员接管、没有紧急停止、桌面操作持有桌面控制权。检查通过后记录操作，再发往虚拟电脑。
- **虚拟电脑的连接**：执行代理在虚拟电脑启动后主动连接平台，并用这台虚拟电脑专属的令牌认证（每次重建容器都会重新签发）；同一台虚拟电脑的执行代理在线时，平台不接受第二个连接。令牌只交给执行代理，虚拟电脑内的其他程序读不到（见[安全说明](security.md)）。不允许访问网络的虚拟电脑通过 Docker Manager 的管理通道连接，这个通道本身证明身份，不需要令牌。实时画面等虚拟电脑内的服务也经由同一连接转发，不对外开放端口。
- **不可用时等待**：虚拟电脑不可用时任务进入等待，超时后失败；恢复后重新执行同一个操作。平台不会改用其他虚拟电脑，也没有在服务器上直接执行的途径。

## 5. 虚拟电脑内部

- **命令**：每条命令在虚拟电脑中以独立的会话运行，完整输出写入日志文件，退出码写入状态文件，因此执行代理重启后仍能从文件得知命令如何结束。等待时间只决定 AI 员工在前台等多久，到时仍在运行的命令转到后台继续运行，多条命令可以同时运行；交给模型的结果只截取一次（按工具输出上限取开头和结尾），并注明日志文件的位置。
- **后台命令的结束**：平台在命令启动之前记录它由哪位 AI 员工、哪段对话或哪项任务在哪台虚拟电脑上启动（`background_commands`）。命令结束时，执行代理向平台报告；连接中断期间结束的命令，在执行代理重新连接时由平台核对补上。结束通知只发送一次：对话收到待读的通知，进行中的任务在下一步读到（定时等待中的任务被唤醒），已结束的任务交给它汇报的对话或记入执行记录。虚拟电脑停止、重启、重置或删除时，仍在运行的命令记为丢失。
- **终端**：交互式的程序使用终端会话，可以输入、读取输出、发送按键、结束整组进程。后台命令和终端会话都不会因为任务或对话结束而被停止，由 AI 员工自己停止。
- **执行代理的分发**：每个虚拟电脑镜像自带一份执行代理，平台镜像也带有一份。Compose 部署中，Docker Manager 启动时把平台镜像中的一份安装到执行代理数据卷：每个版本一个目录（版本号是程序文件的哈希），`current` 指向当前版本并以原子方式切换，保留之前的几个版本；安装命令在 Docker Manager 自己的容器中以 root 执行，文件全部属于 root。这个数据卷以只读方式挂载到每台虚拟电脑的 `/opt/witden/runner-live`。虚拟电脑的启动进程（`witden-init`）每次启动执行代理时选择：数据卷中的版本与这台虚拟电脑兼容（Node.js 版本和启动进程的协议版本）、文件全部属于 root 且其他用户不可写时使用它，否则使用镜像自带的一份；平台安装的版本启动后反复立即退出时，也改用镜像自带的一份，直到出现新的版本。管理通道（`--stdio`）中的执行代理按同样的规则选择。
- **执行代理的更新**：启动进程每 20 秒检查一次数据卷，发现新版本后通知执行代理。执行代理继续处理请求，直到没有进行中的操作（包括模型访问的请求）时断开连接并退出，最多等待 10 分钟，届时仍未完成的操作被中断，平台按结果不确定处理；启动进程随即启动新版本，新版本重新连接平台。命令和终端会话运行在执行代理进程之外，新版本从文件接管命令，终端会话和桌面浏览器照常使用。执行代理在连接时报告自己的版本和来源（随平台更新或镜像自带），平台随虚拟电脑保存并显示在虚拟电脑页。
- **旧版执行代理**：执行代理在连接时报告自己支持的操作。不支持后台命令的旧版执行代理（重置之前的虚拟电脑）仍按原来的方式执行命令，超过等待时间即结束。
- **桌面**：图形桌面支持截图和键鼠操作；实时画面分为只读和可操作两路，只有正在接管的管理员能连接可操作的一路。
- **浏览器**：“桌面”模式使用桌面上可见的浏览器，管理员可以观看和接管；“后台”模式使用不显示的浏览器，不占用桌面。
- **模型访问（可选）**：开启后，执行代理在虚拟电脑内提供 OpenAI 兼容、Anthropic 和 System One 接口，把请求转回平台；平台核对签发的密钥和允许的模型后，用真实的服务地址和密钥调用模型，并按虚拟电脑统计用量。
- **其他程序**：管理员或 AI 员工可以在虚拟电脑中安装和运行任何程序。平台只管理自己的 AI 员工，不单独管理这些程序；它们的能力以虚拟电脑本身的边界为限。

## 6. 共享与接管

- 同一台虚拟电脑上的多位 AI 员工可以同时执行命令；鼠标、键盘和可见浏览器同一时间只由一个持有者使用（桌面控制权），任务等待、暂停或结束时自动释放。
- 管理员接管虚拟电脑时，这台虚拟电脑上的 AI 工作暂停，直到交还。接管需要浏览器持续确认：离开页面、浏览器标签在后台超过 30 秒或 5 分钟没有操作时，控制台自动交还；浏览器异常关闭时，接管在约 3 分钟后失效，平台自动恢复被暂停的工作。

## 7. 可靠性

- **持久队列**：对话的每一轮、任务、入站事件和出站消息都保存在 PostgreSQL 中，由多个进程安全地并发领取；进程崩溃后，未完成的工作由其他进程接手。对话的待读列表与“这一轮是否还在进行”在同一把行锁下判断，消息不会落在一轮结束和下一轮开始之间而无人处理。
- **操作结果不确定时**：有副作用的操作在连接中断后不会自动重做。平台先向执行代理查询该操作的记录：已完成就使用真实结果；无法确认就如实告诉模型“结果不确定”，由它先检查当前状态再决定。启动命令时连接中断也是如此：执行代理的记录表明命令已经启动，平台就继续等待它的结果；无法确认时，命令如果在运行，结束时照常通知。
- **不重复执行**：入站事件按消息去重；出站消息按“消息 × 目标频道”只发送一次，失败可见且可以重试；执行代理按请求编号去重。
- **事务与通知**：数据库事务保持简短，模型调用和虚拟电脑操作都在事务之外进行；实时事件在事务提交后才发出，因此控制台不会看到随后被撤销的数据。

Webhook 与定时触发由 API 进程接收和调度。Webhook 先校验来源密钥、持久保存原始请求，再响应发送方；过滤代码在无主机访问能力的 JavaScript 解释器中执行，通过后才将事件交给指定的 AI 员工。过滤后的消息、对话收件箱和触发状态在同一事务内提交，AI 员工仍由 Worker 执行。定时计划保存下一次执行时间，API 进程每 5 秒扫描，行锁和唯一键防止多个 API 实例重复调度。处理租约超过一分钟可被重新领取，最多三次，领取标识防止旧处理者提交结果。停机错过多次计划时合并补一次。

Webhook 触发器都经 Webhook 来源（`/api/hook-sources/<编号>`）接收，一个来源可以供多个话题的触发器使用：每个请求按来源去重，原始请求只在 `webhook_receipts` 保存一份，再为每个使用它的启用触发器生成一条触发事件，各自过滤和处理。触发器本身没有密钥；旧版本触发器的地址 `/api/hooks/<编号>` 指向升级时由它转成的同一编号的来源。

触发器使用接收时的快照：处理的 AI 员工、补充说明和过滤代码；真正交给 AI 员工前重新检查话题状态、触发器启停、配置人和 AI 员工权限。原始请求按话题保留，列表不加载正文，详情按编号读取；AI 员工的历史工具固定限定在当前话题。

## 8. 实时更新

控制台通过事件流实时接收新消息、任务状态、AI 员工的工作进展和虚拟电脑状态。每个事件在推送前都会重新检查接收者能否查看；接收者都是管理员，可以看到全部会话。

配置发生变化时（AI 员工、账号、模型、虚拟电脑、通讯接入、知识空间、平台设置），无论是在另一个浏览器中由人修改，还是由系统管理员修改，平台都会通知所有打开的控制台“哪一类配置变了”，相应的列表和侧边栏自动重新读取，不需要刷新页面。通知中只有类别，不含配置内容。

控制台在原有内容上更新工作状态：Markdown 渲染组件保持稳定，避免重新挂载已绘制的图表、图片和表格；同一段对话的执行记录刷新时保留上一份数据。流式进展跨模型和工具阶段连续显示，正式消息到达后替换对应的临时进展。滚动跟随同时考虑消息更新和图片、图表的异步尺寸变化，只在读者停留于底部时自动执行。

执行进度摘要以服务端的模型用量记录和电脑操作日志统计轮数、token 与命令数；输入、输出和缓存命中 token 按当前运行累加，缓存命中率使用累计缓存命中数除以累计输入数，无输入时不计算比例。执行记录写入后，只向所在话题发送不含正文的更新通知；控制台默认读取统计和平台系统工具的摘要，直接在对话中列出记忆、配置、协作等操作；服务端先筛选平台调用再分页，不下载思考、输入及电脑操作记录。展开完整过程后分批读取全部记录，逐行展开时再读取完整保存内容。所有读取沿用任务及话题的权限检查，并遮盖密钥、排除图片原始数据。工具请求和结果按调用编号合并；增量刷新保留展开状态和滚动位置，记录区保持固定高度。消息流用同一组稳定键排列回复和执行摘要；运行完成后摘要移到该运行最后一条回复下方，保留已展开内容。历史页面根据消息关联的运行编号恢复摘要，收起只隐藏过程，不删除入口。

## 9. 数据存储

| 数据 | 位置 |
|---|---|
| 账号、外部成员、AI 员工、话题、消息、AI 员工的对话与上下文、任务、审批、审计、用量 | PostgreSQL |
| 模型密钥、通讯凭据 | PostgreSQL，使用主密钥加密 |
| 触发器、Webhook 来源、原始 webhook 请求与处理历史、定时计划 | PostgreSQL；来源密钥保存哈希和加密副本（供校验签名和控制台复制），历史保留至手动清理 |
| 话题关联、AI 员工之间的对话授权（`roles.allowed_contacts`）、AI 员工的技能（`role_skills`）和技能文件的路径与属性（`role_skill_files`）、独立任务的补充输入、历次交付与进展记录 | PostgreSQL |
| AI 员工执行的命令：启动者、虚拟电脑、状态、退出码、时间、日志文件位置和结束通知的去向 | PostgreSQL（`background_commands`）；命令的完整输出在虚拟电脑的日志文件中 |
| 话题文件、头像、技能文件的内容 | 平台数据目录 |
| 虚拟电脑的文件 | 每台虚拟电脑的 Docker 数据卷 |
| 虚拟电脑备份 | Docker Manager 的数据目录 |
