# 关联话题、Webhook 来源与任务续做

本文介绍三项让角色跨话题持续工作的功能：话题之间的关联、多个话题共用的 Webhook 来源，以及已完成的独立任务的补充要求。话题仍然各自保留上下文；关联只允许角色主动发送消息，不复制聊天记录。

## 1. 关联话题

在话题右侧栏的“设置 → 关联话题”中选择另一个话题，确认后两个话题互相关联。只有直接关联的两个话题之间可以发送：A 与 B、B 与 C 分别关联，不表示 A 可以发给 C。

- **私信**：关联私信前需要再确认一次。私信的历史不会开放给对方，但角色发出的文字会被对方话题里的人看到；私信里的角色在这段私信的对话中处理关联过来的请求。
- **权限**：关联本身就是授权。两个直接关联的话题之间，话题中的角色可以互发消息、把任务委托给对方话题中的角色，不需要角色权限，也不需要审批。关联不代替“读取其他话题”权限，角色仍然读不到对方话题的记录。系统管理员角色不参与跨话题发送和委托。
- **解除关联**：之后不能再发送；接收方还没读到的关联消息作废，由关联请求开始的独立任务结束。角色在接收方话题里的对话照常继续，不受影响。

## 2. 发送消息

角色用 `send_message` 发消息。不填 `topic_id` 时发在当前话题；填写直接关联的话题时，发往那个话题：

- **内部话题**：消息交给那里的角色，进入它在那个话题里的对话。同一个角色可以在两个话题之间给自己传递工作。有多个可选角色时，由话题的调度模型挑选一个，也可以用 `role` 参数指定；关联过来的消息总会交给一个角色，不会被调度为“不交给任何角色”。
- **外部频道**（Slack、飞书、GitHub）：消息只发布到对应的平台，不在 witden 中再运行那个话题的角色。平台上的人回复后，按原来的接入规则处理。
- **线程**：`thread` 是目标话题中的消息编号。
- **来源**：一次对话处理多件事时，用 `source_message_id` 指出相关的消息，用 `task_id` 指出相关的独立任务。原始请求人、来源话题和自动轮次由系统记录，模型不能指定；跨话题的每一次发送都计入自动轮次上限（`WITDEN_MAX_AUTO_ROUNDS` 或话题设置中更小的值）。

两个话题没有直接关联，或目标话题中没有可以接收的角色时，发送失败，角色会得到原因并在话题中说明。

发送是异步的：工具先返回消息编号和状态。发往外部频道的消息经出站队列发送，进入队列不等于平台已经收到。同一次工具调用重试时，不会重复发送。

## 3. 派活与回报

外部频道里的角色先理解请求：普通的问答直接回答；需要项目上下文、开发环境或较长的工作时，用 `send_message` 交给关联的内部话题。内部话题接手后，发送方不再重复做同一件事。

内部话题有必要的进展、遇到阻塞、需要人来决定或完成一轮交付时，用同一个工具发回相关的外部频道。工作结果不会自动广播给所有关联的频道。

两个内部话题之间，需要对方完成一项工作并交回结果时，角色用 `delegate_task` 并填写对方话题的 `topic_id`：任务在对方话题中由那里的角色完成，回答发在那个话题里，结果回到发起委托的角色。由委托开始的任务在关联解除后结束。

建议在外部频道话题的“工作说明”中写清它负责哪些沟通、哪些工作交给哪个关联话题，在内部话题中记录项目约定。角色在每次读到新消息时会看到当前的关联列表。

## 4. Webhook 来源

所有 Webhook 触发器都通过“通讯接入 → Webhook 来源”中的来源接收，一个来源可以供多个话题的触发器使用。添加来源、复制地址和密钥的步骤见[使用指南](user-guide.md#28-webhook-与定时触发)；密钥由系统生成，控制台账号可以在来源卡片上随时复制。发送方可以把密钥放在请求头中：

```http
POST /api/hook-sources/<来源编号>
Authorization: Bearer <密钥>
Idempotency-Key: <稳定的事件编号>
Content-Type: application/json
```

也可以按 [Standard Webhooks](https://www.standardwebhooks.com/) 规范用密钥签名：密钥采用规范的 `whsec_<base64>` 格式，支持该规范的发送方（包括 Svix 及兼容平台）直接填入即可，签名放在 `webhook-id`、`webhook-timestamp`、`webhook-signature` 请求头中（`svix-*` 等效）。

- **接收**：单次请求正文最多 1 MiB。请求头中的密钥在读取正文之前校验；签名覆盖正文，读取正文之前只检查来源和时间戳（与服务器时钟相差不超过 5 分钟），读取后再校验签名。凭据不对时返回 401。接收成功返回 202，正文只有请求编号；同一来源、同一事件编号的请求只处理一次，重复时返回 200；签名请求的事件编号是签名覆盖的 `webhook-id`，其他请求是 `Idempotency-Key`。这个地址开放在事件端口上，反向代理需要放行。
- **触发器**：在话题右侧栏的“触发器”中新建 Webhook 触发器时选择来源；还没有合适的来源时，点击“新建 Webhook 来源”跳转到通讯接入添加。每个触发器分别过滤、分别处理。原始请求只保存一份，认证相关的请求头在保存前遮盖。
- **处理方式**：触发器交给它的处理角色处理；在外部频道对应的话题中，处理角色就是机器人代表的角色，结果发到频道。也可以把触发器建在内部话题，由那里的角色处理后，再通过关联把结论发到外部频道。
- **清空历史**：清空话题的触发历史时，不再被任何话题引用的原始请求一并删除；之后同一编号再到达，会作为新请求处理。
- **原来的独立地址**：旧版本中有自己密钥的触发器在升级时转为来源，来源编号就是原触发器编号，密钥不变；`/api/hooks/<编号>` 继续可用，与 `/api/hook-sources/<编号>` 等价。

## 5. 角色管理触发器

在角色的权限中开启“自动化管理”后，角色可以用 `manage_automation` 查看、测试、新建、修改、停用和删除自己负责的触发器，范围是它参与的话题。新建角色的这项权限默认为“询问”，默认每次调用都需要管理员批准；管理员也可在审批卡片中选择“本次运行内允许”，仅免除该次运行内同一工具的重复审批。设为“始终允许”则不再逐次批准，后续运行也适用。

- 角色不能修改其他角色的触发器，不能更换负责人和所在话题，不能读取、设置或重新生成密钥。
- 新建 Webhook 触发器或改用其他来源时，来源设置中的“允许自主订阅的角色”需要包含这个角色；管理员在控制台中配置时不受这个限制。
- 只有控制台账号请求的工作中才能使用这个工具；Webhook 内容、外部成员的消息和其他自动事件不能借此修改配置。

## 6. 已完成任务的补充要求

已完成的独立任务可以补充要求：在任务页点击“补充要求”，或由拆出这项任务的那段对话调用 `continue_task`。任务在原来的执行记录和虚拟电脑上接着做，完成后再交付一次结果，送回发起它的对话。

- **范围**：角色只能续做自己这段对话用 `start_task` 拆出的任务；别的角色委托给它的任务、控制台或触发器开始的任务，由人在任务页补充要求。
- **正在进行的任务**：补充的要求在下一步读到，不打断正在执行的命令。暂停、审批、等待资源或等待子任务时，补充要求不会让它继续。失败或取消的任务先由人重试。
- **重新开始时的检查**：话题和角色必须仍可用，角色仍在原来的虚拟电脑上；角色已换到别的虚拟电脑时，请给它一个新任务。重新开始时使用角色当前的模型、提示词和思考程度。
- **历次交付**：任务页的“历次交付”列出每一次的结果，之后的交付不会覆盖之前的；每次交付按“任务 × 第几次”送回对话，不会被当成重复结果丢弃。
- **长任务**：独立任务的上下文不会自动整理，多次补充要求后可能达到模型的上下文上限；较长的工作请拆成新的任务。

## 7. 数据迁移

升级时自动执行迁移：

- `0039_topic_collaboration`：新增话题关联、Webhook 来源与原始请求、任务输入和交付历史，已结束的独立任务的结果记为第一次交付。
- `0040_webhook_sources_only`：有自己密钥的 Webhook 触发器各转为一个来源（编号和密钥不变），之后触发器不再保存密钥。
- `0041_webhook_source_secret`：Webhook 来源增加加密保存的密钥，用于在控制台中复制；之前的来源只有哈希，重新生成密钥后才能复制。

升级前请备份数据库；回退版本时，停止服务后用升级前的备份恢复数据库。
